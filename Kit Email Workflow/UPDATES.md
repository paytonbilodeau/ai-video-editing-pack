# Keep the pack, lessons and community aligned

Use this checklist when a change affects what readers can do, how they set up
the pack, or which instructions they should follow. Examples include a new
editing route, a changed setup step, a corrected limitation or a moved resource.
A spelling fix usually needs only the affected page and changelog, not a new
announcement.

Start from the current source and inspect each destination before editing.
Record the change in one sentence, identify the affected lessons and keep a
recoverable copy of their current content. Update only the destinations whose
instructions or claims would otherwise become inaccurate.

## 1. GitHub and the downloadable pack

Update the relevant public skills, guides and generic lesson templates. Keep
private transcripts, visual recipes, account identifiers, subscriber data and
credentials outside the repository. Preserve existing setup and download URLs.
Record the version and concrete changes in the changelog; do not describe a
documentation correction as a new feature.

Review the exact diff, check links and privacy, and run the required tests.
Use the repository's protected pull-request process. After merge, build any
changed standalone pack from the merged source, test a fresh extraction and
publish the release. Download the public ZIP again and compare its checksum
with the tested build. Check any retained legacy download route too. A merged
source change does not update an existing release asset.

## 2. The email sequence

Compare the current live lesson with the reviewed source. Update the explanation
and links that changed while preserving sender settings, lesson order, delivery
delays, sending days, illustrations and the provider's unsubscribe footer.
Save only the affected lessons and reopen them to verify that the changes
persisted. Check the actual desktop and phone previews, including tracked links.
Record which lessons were verified; do not call a saved draft a live update.

The optional community invitations in these templates appear only in lessons
1, 5, 9, 13, 18 and 22. Keep one short P.S. after the signature, with visible
paragraph spacing. Where a P.S. already exists, preserve it and add the
invitation as P.P.S. Use the invitation that fits the lesson: read ahead, ask
for help, explore a style, request feedback, share finished work or stay in
touch. Replace `YOUR_COMMUNITY_URL`, verify the promised resources, or remove
the invitation if there is no community. These placements do not change the
immediate first lesson or daily sequence cadence.

## 3. The community classroom and announcement

Update the matching classroom lesson and any affected resource links. Preserve
its existing illustrations, order and useful explanations. Compare the rendered
page with the relevant email and public guide, then reopen it to confirm the
saved content. Readers should receive the same instructions in each location.

After the relevant release and lesson updates are verified, publish a concise
announcement only to destinations authorized by the owner. Explain what changed,
who it helps and where to find it. Avoid repeating an announcement for the same
release. Check the actual live post and its links; submitting a post or receiving
a queued status is not proof that it is visible.

Keep one private receipt with the version, affected lessons, public links,
checksums, verification results and any remaining gap. Record each destination
separately as drafted, saved or live. Do not claim that the funnel is synchronized
while one required destination remains stale. This checklist does not create
an automation or grant access to anyone's accounts.
