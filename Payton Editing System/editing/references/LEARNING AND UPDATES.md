# Learn from an edit without losing your choices

Use version, timestamp, observed problem and requested change. Duplicate the timeline, change the affected range and replay it in context. For a returned manual edit, compare the actual source/output map and picture/audio properties against the saved baseline. Distinguish trims from ripple movement and rounded API fields. Keep accepted framing and audio through a narrow repair.

Save a reusable preference only when the evidence supports it. A one-video joke pause, particular mask, microphone setting or sign-off removal can remain project-only. Record source/date/scope, current wording and proposed replacement. Do not turn a local dB value, frame count or number of cuts into a universal target. Updating a file does not retrain model weights.

Keep the bundle reference separate from the user's editable profile and project records. For an update, compare three things: original clean release, customized working copy and new release. Keep user-only files, use upstream changes where the user did not customize, and review both-sides edits. With no clean original, differences remain uncertain rather than being presumed safe. Use a separate candidate and a recovery copy; verify the saved result before switching.

Private source changes are reviewed through the product's existing release process. The distributed source manifest names modules and portable hashes; no customer update requires access to Payton's machine or private files. A new source version is not automatically an approved public release. This feature's public-release hold is managed by the existing member-first policy, outside the product instructions.
